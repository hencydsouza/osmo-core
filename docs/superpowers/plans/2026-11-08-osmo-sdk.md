# osmo SDK Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship one native library (`osmo_ffi`) with Swift and Kotlin bindings that macOS and Android apps can use to list, download, star, delete and trim files on a DJI Osmo camera, with no ffmpeg inside.

**Architecture:** Pure-Rust MP4 trim goes in `osmo-core`; a blocking high-level `Camera` API goes in a new `osmo-sdk` crate (taking over the listing/planning logic and download orchestration now in `osmo-cli`); a new `osmo-ffi` crate wraps it with UniFFI proc-macros. The CLI is rebuilt on `osmo-sdk`. Bluetooth stays in the apps, behind a foreign-implemented `BleLink` callback interface.

**Tech Stack:** Rust 2021, UniFFI 0.29 (proc-macros), cargo-ndk, Swift 5 (SwiftPM test), Kotlin + Gradle + Android emulator (arm64-v8a), ffmpeg/ffprobe **only as test oracles**, never linked.

**Spec:** `docs/superpowers/specs/2026-11-08-osmo-sdk-design.md`

## Global Constraints

- `osmo-sdk` and `osmo-ffi` must not depend on btleplug, tokio, clap, or spawn a process.
- ffmpeg/ffprobe are used only in tests and are skipped, not failed, when absent.
- `ureq` is used with `default-features = false` (no TLS; the camera speaks plain HTTP at `192.168.2.1`).
- All 298 existing tests keep passing after every task; `cargo clippy --workspace --all-targets -- -D warnings` stays clean.
- Output files are written to `<dest>.part` and renamed on success; a failed or cancelled run leaves no file at `dest`.
- No panic may cross the FFI boundary; every exported call returns a typed error.
- Camera writes (`star`, `delete`) keep today's guards: fresh session, verified unshared handle, all-or-nothing.
- Every claim of "tested" in docs states unit/fixture vs live (emulator, real camera).
- DJI MP4 layout to support (observed 2026-11-08 on the Action 4): `ftyp, free, mdat, moov` with `moov` **last**; tracks: video (`hvc1` or `avc1`, has `edts/elst`), audio (`mp4a`), data `djmd` (one sample per video frame), `tmcd` (one sample), and an `mjpeg` cover track with no normal sample table in the proxy.

## Review Focus

- Range outside the clip (`from >= to`, `from` past the end, `to` past the end): clear error or a clamped result with the real duration reported, never an empty or corrupt file.
- Files whose `moov` is first (faststart), or that use `co64` (offsets above 4 GiB): parse and trim identically.
- Tracks that are not video/audio (`djmd`, `tmcd`, cover image): trimmed in step with the video or kept intact, and never able to make the output unplayable.
- The connection dropping mid-range-read, or the user cancelling: error returned, no half-written file at `dest`, no hang.
- An exported FFI call that panics or is handed a bad path/UTF-8/negative time: typed error, process survives.

### Task 3: Trim planner (pure)

**Files:**
- Create: `osmo-core/src/mp4/plan.rs`
- Test: `osmo-core/src/mp4/plan.rs` (`mod tests`, built from hand-made `Movie` values)

**Interfaces:**
- Consumes: `Movie`, `Track`, `Sample` (Task 2).
- Produces:
  - `pub struct TrackCut { pub track: usize, pub first: usize, pub end: usize }` (sample index range `first..end`)
  - `pub struct TrimPlan { pub cuts: Vec<TrackCut>, pub actual_start_secs: f64, pub duration_secs: f64 }`
  - `pub fn plan_trim(movie: &Movie, from_secs: f64, to_secs: f64) -> Result<TrimPlan, Mp4Error>`

Rules the tests pin: the first video track decides the start: the cut begins at the last sync sample with `dts <= from`; the end is the first sample with `dts >= to` (end clamps to the clip's end and the clamped duration is reported, not an error); every other track starts at the first sample with `dts >= actual_start` in its own timescale, and ends at the same instant (the `djmd` track therefore keeps its sample-per-frame alignment); a track with a single sample (`tmcd`) is kept whole; a track with no samples is dropped from `cuts`. `from < 0`, non-finite, `from >= to`, or `from` at/after the clip end → `BadRange` naming the clip length.

- [ ] **Step 1: Write failing tests:** `start_snaps_back_to_the_previous_sync_sample`, `end_is_exclusive_and_clamps_to_clip_end_reporting_real_duration`, `audio_and_data_tracks_cut_at_the_same_instant`, `single_sample_timecode_track_is_kept_whole`, `empty_tracks_are_dropped`, and a table test over bad ranges (`-1`, `NaN`, `5..5`, `9..3`, `from` beyond end) each asserting the `BadRange` message contains the clip length.
- [ ] **Step 2:** Run → fail. **Step 3:** Implement `plan_trim` (binary search on `dts`). **Step 4:** Run → pass.
- [ ] **Step 5:** Commit `feat: pure trim planner`.
